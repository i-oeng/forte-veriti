# Описание решения для жюри — Datathon 26, кейс ForteBank

**Сервис:** AI-проверка кассовой дисциплины по видеозаписям (локальные модели, без облачных AI-сервисов).

## 1. Адреса и доступ

| Что | Где |
|---|---|
| Веб-интерфейс | https://forteveriti.tail8331b7.ts.net/ |
| API (раздел 10) | `POST https://forteveriti.tail8331b7.ts.net/api/v1/analyze` (поле `file`) → `job_id`; `GET https://forteveriti.tail8331b7.ts.net/api/v1/jobs/{job_id}` |
| API-ключ | передаётся жюри отдельно; заголовок `X-API-Key`, запросы без верного ключа получают 401 |
| Документация API | https://forteveriti.tail8331b7.ts.net:8443/api/docs |

```bash
curl -X POST https://forteveriti.tail8331b7.ts.net/api/v1/analyze -H "X-API-Key: <ключ>" -F "file=@video_017.mov"
curl https://forteveriti.tail8331b7.ts.net/api/v1/jobs/<job_id> -H "X-API-Key: <ключ>"
```

Ответ — ровно по схеме из раздела 10: `job_id`, `status` (`processing` / `done` / `failed`), `verdict`
(`violation` / `no_violation`), `violations[]` с полями `type`, `timecode_sec`, `description`, `evidence_frames`
(1–3 JPEG в base64; первый кадр — лучший, его время совпадает с `timecode_sec`). Обработка одного видео —
обычно 40–180 секунд, жёсткий внутренний лимит 270 секунд (меньше 5 минут). Несколько видео обрабатываются
параллельно (проверено: 12 видео одновременно, все готовы за 181 с).

## 2. Как пользоваться

1. Открыть веб-интерфейс и перетащить один или несколько файлов `.mov`.
2. Для каждого видео видны этап и процент обработки.
3. Результат: «Нарушение не обнаружено» или «Обнаружены признаки возможных нарушений». Для каждого события —
   тип, таймкод (клик переводит плеер на этот момент), кадры-доказательства, описание того, что видно и почему
   это может быть нарушением, норматив (название акта, пункт, ссылка на adilet.zan.kz, о чём этот акт),
   короткий фрагмент видео.
4. «История проверок» — ранее проверенные через интерфейс видео.

Запуск сервиса с нуля описан в `README.md` (раздел Running): три systemd-сервиса (`forte-vllm`, `forte-api`,
`forte-worker`), nginx и Tailscale Funnel для публичного адреса; пользователю ничего запускать вручную не нужно.

## 3. Архитектура, подход, модели

```
загрузка .mov → API (FastAPI) → очередь (SQLite) → обработчик (4 видео параллельно, бюджет 270 с)
 0. нормализация   любой принятый формат (.mov, .mp4, .avi, .mkv, .ts, .mts, .m2ts, .mpg, .mpeg, .m4v, .webm) → MP4 через ffmpeg
 1. декодирование   ffmpeg, 5 кадров/с; поворот, HEVC, любые разрешения, обрезка чёрных полей
 2. восприятие      RF-DETR (люди только как силуэты-рамки; телефоны, чашки, сумки) + трекинг ByteTrack
 3. события         входы, выходы, перемещения, сближение людей, появление предметов (точное время)
 4. разметка сцены  VLM один раз на видео находит сейф, дверь и стол — новый ракурс не требует калибровки
 5. факты           VLM отвечает на вопросы о ФАКТАХ, а не о нарушениях (сколько людей, открыт ли сейф,
                    что в руках у кассира, работает ли счётная машина …); ответ — JSON по схеме (xgrammar)
 6. ключевые моменты крупные планы в решающие моменты: кассир ушёл (что осталось на столе, экран ноутбука,
                    сейф, ключ), кто-то вошёл (лежат ли деньги), визит клиента (показан ли документ),
                    инкассатор (проверена ли сумка); дверь — по пикселям, без VLM
 7. правила         факты + моменты + восприятие → нарушения с ID из каталога и точным таймкодом
 8. обзор           открытый обзор VLM для того, что не сводится к фактам (деньги вне поля зрения, замена
                    купюр, «иное» — новый тип, который модель называет сама) + отдельная перепроверка да/нет
 9. доказательства  самый резкий кадр в момент события и ±2 с, клип 8 с, аннотированные кадры
```

**Почему факты и правила.** Небольшая VLM на вопрос «есть ли нарушение?» почти всегда отвечает «да» (около
55 % точности в наших тестах), а на вопросы о фактах отвечает верно примерно в 80 % случаев. Правила дают
точный таймкод и объяснение, которое проверяющий может проверить по кадру.

| Роль | Модель | Лицензия |
|---|---|---|
| Визуально-языковые модели (VLM) | Qwen3.5-4B (AWQ 4-бит) через vLLM 0.31 — факты по кадрам; Qwen3.5-27B (AWQ 4-бит) — второй контролёр по всему ролику; сравнивались Qwen3.5-9B, Qwen3-VL-8B, InternVL3.5-14B, InternVideo2.5-8B, Cosmos-Reason2-8B | Apache-2.0 (Cosmos — NVIDIA Open Model License, коммерческое использование разрешено) |
| Детектор людей и предметов | RF-DETR Small (COCO) | Apache-2.0 |
| Трекер | ByteTrack (`trackers`) | Apache-2.0 |
| Видео | FFmpeg | LGPL/GPL (CLI) |
| Сервис / интерфейс | FastAPI, SQLite / React, Vite | MIT / public domain / MIT |

**Локальность и переносимость.** Все модели работают внутри сервиса на нашем сервере (GPU 8 ГБ). Облачные
AI-сервисы не используются, видео и кадры никуда не передаются. После загрузки весов интернет не нужен:
модели читаются с диска, включены `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, статистика vLLM отключена;
при наблюдении за процессами сервиса во время анализа исходящих соединений не было.

**Лица не распознаются.** Люди обрабатываются только как силуэты (рамки тела).

**Тестовые видео.** Исходный файл удаляется сразу после анализа. Для заданий, пришедших через API жюри, не
создаётся копия для просмотра, их кадры и клипы не раздаются по ссылкам, они не видны через интерфейс и не
попадают в историю.

**Принцип.** Для каждого типа в каталоге (`app/catalog.yaml`) задано: что именно должно быть видно на видео,
какие факты и моменты это подтверждают, акт, пункт и формулировка требования. Ссылки на нормы берутся только
из каталога, модель их не придумывает. Описание каждого события строится из трёх частей: что видно (с
временем), почему это может быть нарушением, норма (акт и пункт), и всегда заканчивается словами «Требуется
проверка сотрудником»: результат — подсказка для человека, а не юридическое заключение. Нарушения, для
которых нужны невидимые на видео данные (проводки, сверка, содержание документов), сервис не утверждает.

**Таймкод** (FAQ 10): для действия — момент его начала; для оставленного (деньги, открытый сейф, ключ,
незаблокированный компьютер) — момент, когда кассир отходит; для пропущенного шага (не показан документ, не
проверена сумка, клиент ушёл до конца пересчёта) — момент, когда этот шаг должен был произойти.

## 5. Типы нарушений, которые распознаёт решение

Уровень A — само нарушение видно на видео; B — видимое требует проверки контекста или документов человеком.

| Тип (ID) | Что должно быть видно | Ур. | Норма |
|---|---|---|---|
| Деньги предыдущего клиента оставлены на столе (`previous_customer_cash_left_exposed`) | наличные лежат на столе, когда кассир уходит или входит следующий человек | A | № 231, абз. 2 п. 20 |
| Пересчёт денег клиента после его ухода (`cash_counted_without_customer_present`) | клиент уходит, а кассир ещё считает или закладывает его деньги в машину | A | № 231, абз. 1 п. 20 |
| Кассир покинул рабочее место во время обслуживания (`cashier_left_during_active_customer_service`) | кассира нет на месте, клиент остаётся | A | № 231, п. 22 |
| Идентификация клиента не наблюдалась (`customer_identification_not_observed`) | деньги переданы, документ, удостоверяющий личность, не показан | B | № 231, пп. 1) п. 19, пп. 1) п. 31 |
| Возможный доступ постороннего в зону кассы (`possible_unauthorized_vault_access`) | другой человек на стороне кассира или у сейфа | B | № 14, п. 8, пп. 1) п. 16 |
| Кассовая операция доступна посторонним (`collection_exposed_to_third_parties`) | третий человек у стола во время операции | B | № 14, п. 21 |
| Дверь кассы оставлена открытой (`cash_desk_access_door_left_unsecured`) | дверь остаётся открытой, пока внутри работают | B | № 14, пп. 1) п. 16, п. 8 |
| Ключ оставлен в сейфе (`KEY_LEFT_IN_SAFE`) | кассир уходит, ключ остаётся в замке сейфа | B | № 231, п. 80, п. 76 |
| Банковские документы или незаблокированный компьютер без присмотра (`BANK_DOCUMENTS_EXPOSED`) | кассир уходит, на столе документы или открытое рабочее окно | B | № 53, пп. 9) п. 71; № 231, пп. 17) п. 2, п. 80 |
| Сейф оставлен открытым (`SAFE_LEFT_OPEN`) | дверца сейфа открыта, у сейфа никого нет | B | № 231, абз. 2 п. 20, п. 80 |
| Инкассаторская сумка принята без проверки (`COLLECTION_BAG_ACCEPTED_WITHOUT_INTEGRITY_CHECK`) | сумку принимают без видимой проверки целостности, пломбы, документов | A | № 231, п. 24 |
| Личные вещи кассира в кассовом узле (`PERSONAL_ITEM_IN_CASH_NODE`) | сумка, одежда, еда на кассовом столе | B | № 231, абз. 1 п. 12 |
| Смартфон с камерой в кассовом узле (`PHONE_WITH_CAMERA_IN_CASH_NODE`) | кассир пользуется смартфоном | B | № 231, абз. 2 п. 12 |
| Обработка наличных без контролирующего работника (`CASH_PROCESSING_WITHOUT_CONTROLLER`) | кассир один пересчитывает деньги из инкассаторской сумки | A | № 231, п. 42 |
| Наличные вне поля зрения камеры (`CASH_OUT_OF_VIEW`) | купюры убирают под стол, в карман, одежду или сумку | B | № 231, абз. 2 п. 20, п. 12 |
| Заменённые банкноты не пересчитаны (`REPLACEMENT_CASH_NOT_RECOUNTED`) | клиент меняет купюры, новые принимаются без пересчёта | A | № 231, пп. 2), 4) п. 19 |
| Иное видимое нарушение порядка (`other`) | новый тип, который модель называет сама (тест может содержать типы вне обучающих данных) | B | № 231 (акт в целом; пункт определяет проверяющий, FAQ 31) |

В каталоге есть ещё 15 типов с проверенными пунктами (сортировка, сомнительные банкноты, выдача без
пересчёта, сверка в конце дня и др.), которые пока не распознаются автоматически.

## 6. Результаты на размеченном датасете (42 размеченных ролика: 22 с нарушением, 20 без)

| Версия | Точность вердикта | Пропуски | Ложные срабатывания | Точность типа | Таймкод ≤ 3 с |
|---|---|---|---|---|---|
| v7, Qwen3.5-4B | 67 % | 5 | 9 | 82 % | 65 % |
| v8, Qwen3.5-4B | 69 % | 4 | 9 | 83 % | 67 % (медиана 2,1 с) |
| v9, Qwen3.5-4B | 73,8 % | 2 | 9 | 80 % | 60 % (медиана 2,1 с) |
| v10 (режим полноты), Qwen3.5-4B | 69,0 % | 1 | 12 | 76 % | 67 % (медиана 1,4 с) |
| v11: v10 + телефон только в руках кассира | 76,2 % | 1 | 9 | 76 % | 62 % (медиана 1,4 с) |
| **v12 (текущая)**: v11 + Qwen3.5-27B вторым контролёром | **73,8 %** | **1** | **10** | 71 % | 67 % (медиана 1,2 с) |

**v10 сознательно меняет точность на полноту:** по условиям кейса пропуск недопустим, а ложная тревога лишь
нежелательна. Находка «деньги вне поля зрения», которую повторная проверка не подтвердила, теперь не
отбрасывается, а показывается с пометкой «не подтверждено» и пониженной уверенностью. Итог: пропусков 1 вместо 2
(найден `Х-1`), ложных срабатываний 12 вместо 9. Режим отключается одной настройкой (`FORTE_RECALL_MODE=0`).
v11 убирает ложные срабатывания по телефону: телефон считается нарушением, только если он у человека на месте
кассира (ближе к сейфу), а не у клиента (`Х-5`, `Х-48`).
**v12 добавляет вторую, более крупную модель (Qwen3.5-27B).** Она смотрит весь ролик и (1) снимает «шумные»
находки лёгкого конвейера, если нарушения не видит (в v12 убраны ложные `Х-16`, `Х-35`), и (2) добавляет типы,
которых лёгкий конвейер не распознаёт (15 справочных типов каталога и типы вне каталога), с низкой уверенностью.
Так найден `Х-44` (пересчёт и сортировка), который v11 пропускал. Цена — та же находка «пересчёт без счётной
машины» на чистых `Х-27`, `Х-43`, `Х-45`. Если вторая модель недоступна, работает лёгкий режим (v11).

Все ролики обработаны быстрее 181 с (лимит 300 с). 42 размеченных строки — это 40 уникальных роликов: `Х-4` и `Х-47`,
`Х-5` и `Х-48` побайтно совпадают (у `Х-4`/`Х-47` два разных размеченных момента). Результаты получены на тех же роликах, на которых
настраивались правила, поэтому на новых съёмках точность, скорее всего, будет ниже.

## 7. Ограничения и известные ошибки

* **Не судим о невидимом.** Проводки, сверки, данные АБИС, содержимое документов на видео не видны; такие
  нарушения сервис не утверждает. Звук по условиям кейса не используется.
* **Мелкие действия рук.** Замена купюр, ручной пересчёт вместо машины, руки под краем стола, деньги вне поля
  зрения — самое слабое место. В v12 пропущен `Х-1` (замена купюр): его находит только неподтверждённая находка
  режима полноты, а она появляется не в каждом прогоне; `Х-44` находит только вторая модель.
* **Мелкие детали.** Ключ в замке сейфа — 3–4 пикселя при 464×848; чаще всего не замечается (`Х-22`, `Х-11`).
* **Стекло и отражения.** Люди за стеклом и отражения мешают подсчёту людей и определению двери.
* **Дверь.** В размеченных роликах «дверь оставлена открытой» по времени открытия (около 3 с) не отличается от
  обычного прохода на чистых роликах: отсюда часть ложных срабатываний (`Х-12`, `Х-31`, `Х-39`).
* **Ложные срабатывания: 10 из 20 чистых роликов (v12).** Дверь на `Х-12`, `Х-31`, `Х-39`; идентификация на `Х-19`;
  неподтверждённое «деньги вне поля зрения» на `Х-8`, `Х-12`, `Х-14`, `Х-21`, `Х-31`; «пересчёт без счётной машины»
  от второй модели на `Х-14`, `Х-27`, `Х-43`, `Х-45`. Набор слегка меняется от прогона к прогону. Мы сознательно
  смещены в сторону полноты: по условиям кейса пропуск хуже ложной тревоги, а каждый результат помечен
  «Требуется проверка сотрудником».
* **Типы каталога.** 17 из 32 типов распознаёт лёгкий конвейер (правила и проверка); остальные 15 и типы вне
  каталога — только вторая модель по всему ролику, с низкой уверенностью и приблизительным временем.
* **Новые типы нарушений.** Лёгкий конвейер принимает неизвестное событие только при подтверждении в 4 и более окнах
  (его собственный открытый поиск шумит на чистых роликах). Новые типы называет вторая модель; на наших 42 роликах
  она ни разу не назвала тип вне каталога (там их нет), поэтому её способность находить новые типы не измерена.
* **Две модели на двух GPU.** Qwen3.5-4B (GPU 8 ГБ) читает факты по кадрам; Qwen3.5-27B (GPU 24 ГБ, отдельный сервер
  команды, доступ по HTTPS с ключом) смотрит ролик целиком. При недоступности второго сервера сервис работает в
  лёгком режиме. Вместо 4B в конвейере модели 8–27B не превзошли её; конвейер настраивался под 4B. Без правил и детектора
  проверенные на сегодня VLM, оценивая ролик целиком, работают на уровне угадывания: решение принимают правила.
* **Настройка на 42 роликах.** Новые ракурсы, освещение, ночная съёмка и другие модели камер не проверены.
  Расположение сейфа, двери и стола определяется заново для каждого ролика, но качество на новых сценах не измерено.
* **Идентификация клиента** (уровень B): документ могут показать вне кадра или в цифровом виде.
* **Детерминизм.** Два одинаковых ролика (`Х-4` = `Х-47`) могут получить разный результат: сервер VLM
  объединяет запросы параллельных заданий в пакеты, это немного меняет вычисления.
* **Одна камера.** Записи нескольких камер одного кассового узла не объединяются.
* Сервис не идентифицирует людей (только силуэты-рамки).

## 8. План развития

* **Два режима развёртывания — оба полностью локальные, без облака.**
  * «Лёгкий»: один GPU 8 ГБ, Qwen3.5-4B + детектор, трекер и правила (v11: 76,2 %, 1 пропуск, 9 ложных).
  * «Полный» (сдаём его, v12): дополнительно Qwen3.5-27B вторым контролёром (`app/pipeline/second_opinion.py`,
    включается `FORTE_SECOND_VLM_URL`). Сейчас модели на двух GPU (8 и 24 ГБ); у банка обе помещаются на один
    локальный GPU 48 ГБ.
* **Следующая версия полного режима — «предложи и проверь» по каждой находке.** Конвейер на 4B с ослабленными
  порогами предлагает кандидатов (время, тип, люди и предметы рядом). Большая модель проверяет каждого: плотный
  фрагмент ±4 с, крупные планы по рамкам детектора и конкретный вопрос для этого типа («Дверь кассы осталась открытой
  после выхода кассира?»). Так полнота берётся от правил, а точность — от большой модели, и вызовов немного.
  Для неизвестных типов большая модель смотрит ключевые моменты (вход, выход, передача, работа у сейфа) с каталогом,
  а найденное вне каталога перепроверяет вторым, иначе сформулированным вопросом; итог — «новый тип», низкая
  уверенность, «Требуется проверка сотрудником».
* **Одна модель на всё** — быстрая MoE-модель (например, Qwen3.6-35B-A3B, 3B активных параметров, Apache-2.0) на одном
  GPU 48 ГБ: и чтение фактов по кадрам, и проверка целого ролика.

* **Дообучение на записях банка в его контуре.** Детектор и VLM (LoRA) — на размеченных записях, без выноса
  данных за периметр; отдельный набор сцен для проверки, а не только для обучения.
* **Устойчивость к новым ракурсам камер.** Набор записей с разных точек установки, аугментации (поворот, обрезка,
  освещение), проверка на сценах, не участвовавших в настройке.
* **Ещё 15 типов из каталога — в автоматику** (сортировка, сомнительные банкноты, выдача без пересчёта, сверка в
  конце дня и др.).
* **Крупные планы рук и денег, более сильная VLM.** Вырезки по рамкам детектора в полном разрешении; модель 8B+
  на GPU 16–24 ГБ.
* **NVIDIA DeepStream + TensorRT — потоковый режим.** Приём RTSP с живых камер, детектор (RF-DETR → TensorRT) и
  трекер на GPU в реальном времени, правила на метаданных, а VLM вызывается только для событий-кандидатов. Это
  десятки камер на один сервер вместо обработки файлов. SDK распространяется по лицензии NVIDIA (бесплатной,
  но не открытой) — согласовать с банком; открытая альтернатива — GStreamer + ONNX Runtime/TensorRT.
* **Модель поз и кистей рук** (например, RTMPose, Apache-2.0, без распознавания лиц): пересчёт, передача и замена
  купюр, руки под столом.
* **Специализированные детекторы:** состояние двери и замка сейфа, купюры, инкассаторская сумка — обученные на
  данных банка вместо общих моделей.
* **Сверка с АБИС и журналом операций:** сопоставление видео с проводками закрывает нарушения, которые не видны
  в кадре.
* **Обратная связь контролёров.** Отметки «подтверждено / ложная тревога» в интерфейсе → калибровка порогов и
  дообучение.
* **Оповещения в реальном времени** для службы внутреннего контроля и безопасности; отчёты по отделениям.
* **Несколько камер одного кассового узла** — объединение в одну картину событий.
* **Масштабирование:** очередь заданий уже поддерживает несколько обработчиков; следующий шаг — несколько GPU и
  серверов.
* **Журнал доказательств для аудита:** кадры, хэши, сроки хранения, кто и когда просматривал.
